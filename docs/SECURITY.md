# rentPC — Security model

## Principals

| Principal | Trust level | What they can do |
|---|---|---|
| Host owner | Untrusted for renter confidentiality; trusted for their own machine | Runs the agent; physically owns the hardware |
| Renter | Untrusted, possibly malicious | Arbitrary code inside their VM |
| Backend | Trusted coordinator | Issues credentials, relays traffic, bills |
| Host agent | Trusted code on an untrusted machine | Enforces isolation on the host's behalf |

## Assets to protect

1. Host's personal files, OS session, browser sessions, credentials.
2. Host's private LAN (routers, NAS, IoT, other PCs) and link-local/metadata.
3. Host agent integrity (a renter must not control it).
4. Renter's workload and data *from other renters* (and, best-effort, from the host).
5. Marketplace integrity: no double booking, correct billing, no credential leaks.

## Isolation boundaries

**Primary boundary: hardware virtualization.** Every rental runs in its own
Linux VM (QEMU with WHPX/HVF/KVM; VZ/Hyper-V later). The guest has:

* its own kernel, its own virtual disk (qcow2 overlay created per rental,
  deleted on termination), no host directories mounted (no 9p/virtiofs/shared
  folders), no USB/PCI passthrough in the CPU tier;
* no access to the host's processes, memory, clipboard, display or input;
* resource caps from `-smp`/`-m` and disk size; host-side the QEMU process runs
  at below-normal priority so the owner's desktop stays responsive.

**Network boundary: no network except two explicit holes.** The VM's NIC
is QEMU user-mode networking with `restrict=on`: the guest gets DHCP from
the virtual gateway but *nothing* is forwarded to the host, the LAN or the
internet. The only two paths are:

* **inbound** — a `hostfwd` bound to `127.0.0.1:<random>` → guest:22, used
  exclusively by the agent (relay streams, web terminal, egress link);
* **outbound** — an HTTP/1.1 forward proxy (CONNECT + absolute-URI) run by
  the agent (`internal/netpolicy`) and published *inside* the guest as
  `127.0.0.1:3128` through an SSH remote forward. The proxy resolves names
  itself and drops any destination in `0/8, 10/8, 100.64/10, 127/8,
  169.254/16, 172.16/12, 192.0.0/24, 192.168/16, 198.18/15, 224/4, 240/4,
  ::1, fc00::/7, fe80::/10`, every IP currently bound on the host, and
  SMTP ports (25/465/587). A hostname that resolves to *any* blocked address
  is refused outright (DNS-rebinding defence).

Consequence: `curl http://10.0.2.2`, scanning the home LAN, or hitting a cloud
metadata service from inside the VM all fail — there is no route. Tools that
honour `http_proxy`/`https_proxy` (pip, npm, apt, Go, curl, most SDKs) work;
raw sockets to the internet do not, which is a documented limitation.

**Container tier (future, explicitly weaker).** A `container` driver for
compute-only jobs shares the host kernel (or, on Windows/macOS, a shared
utility VM). It is *not* VM-equivalent: a kernel exploit escapes to the host or
to other tenants. If shipped it is labelled "compute-only / reduced isolation"
in the listing, disabled by default, and never offered on a host that also
has the owner's personal data unless the owner opts in.

## Credentials

* **Renter → VM**: per-rental ed25519 keypair generated by the backend; the
  public key is injected via cloud-init, the private key is encrypted at rest
  and delivered once over HTTPS, then its ciphertext is deleted when the
  rental ends. Password auth is disabled in the guest.
* **Agent → backend**: a long random host token exchanged for the one-time
  registration token from the web UI; stored hashed (SHA-256) server-side,
  stored in the OS keychain / `0600` file client-side. Rotatable.
* **Renter → relay**: session cookie or API key; tunnel/terminal endpoints
  verify the renter owns the rental and it is in `ready|active`.
* **Backend → agent**: streams are only opened by the backend inside the
  agent's own outbound yamux session; the agent never listens on any port.

## Threats and mitigations

| Threat | Mitigation |
|---|---|
| Renter escapes VM | Hardware virt, no shared folders, minimal device set (`-nodefaults`), pinned QEMU version, non-admin QEMU process, cleanup on termination. Residual: hypervisor 0-day — accept, monitor advisories. |
| Renter scans/attacks host LAN | `restrict=on` leaves no route; the egress proxy refuses private/host ranges (unit-tested in `netpolicy`). Milestone 2d verifies from inside a real VM. |
| Renter abuses outbound (spam, DDoS, crypto-mining) | Per-rental bandwidth accounting, port 25 blocked by default, reputation + ban; hosts can set an egress allow-list later. Mining is allowed-but-metered (it is compute). |
| Renter controls the agent | Agent exposes no API to the guest; control comes only from the backend over the authenticated tunnel. |
| Malicious host reads renter data | Unavoidable at the hardware level. Mitigations: documented "don't put production secrets on rented hosts", host reputation + verified identity, encrypted-at-rest renter disks (key held by renter, lost on reboot) later, TEE/attestation out of scope for MVP. |
| Malicious host lies about hardware | Agent-reported specs are cross-checked with a benchmark run inside the first VM; renters rate. |
| Double booking | DB partial unique index + state-guarded transitions (ARCHITECTURE §5–6). |
| Reservation squatting | Reservations expire after 5 min unless the rental progresses; sweeper enforces. |
| Credential leakage via logs | Private keys and tokens are never logged; redaction middleware on API logs. |
| Stolen session cookie | httpOnly, Secure, SameSite=Lax, server-side sessions with revocation, 7-day expiry. |
| Password attacks | argon2id, per-account + per-IP rate limiting on `/auth/login`. |
| Host disconnect mid-rental | Grace period; rental marked failed and prorated; on reconnect agent reconciles and destroys orphaned VMs. |
| Agent binary tampering | Signed releases, version pinned by backend minimum; later: attestation. |
| Relay compromise | Relay sees SSH ciphertext only for native-SSH tunnels (end-to-end between renter's ssh and the guest sshd). Web-terminal PTY traffic is plaintext inside the relay — documented; native SSH recommended for sensitive work. |

## Hosts behind TLS inspection (Netskope, Zscaler, antivirus "HTTPS scanning")

Such hosts re-sign every HTTPS connection with a private CA that only the
host trusts. A rental VM has a clean trust store, so renters' `pip`, `git`
and API calls fail with certificate errors. This is the *correct* outcome:
installing the interceptor's CA into renter VMs would hand the host's
employer (or AV vendor) every renter's plaintext. rentPC therefore never
does that; instead `rentpc-host doctor` and the agent's startup log detect
interception and tell the host to use a network without it. A later
version can mark such hosts "HTTP-only / restricted egress" in the
marketplace.

## Operational limitations (honest list)

* Consumer laptops with hybrid graphics: no GPU in a VM; CPU-only.
* Windows Home: WHPX only (no Hyper-V); WHPX is adequate but slower.
* macOS: never any GPU access; VZ requires signed agent builds.
* The host owner must leave the machine on and awake; the agent prevents
  sleep while a rental is active and *refuses* new rentals when on battery.
* Antivirus on Windows may flag QEMU; documented in the host install guide.

## Secure defaults checklist (for code review)

- [ ] No host path ever appears in a QEMU command line except the per-rental
      work directory under the agent's data dir.
- [ ] Guest NIC always `-netdev user,restrict=on`; the only hostfwd is loopback → :22; no `guestfwd`.
- [ ] `Destroy` shreds overlay + seed and is idempotent; invoked on every exit
      path including agent crash recovery (state file).
- [ ] All lifecycle transitions are `UPDATE … WHERE status = $from`.
- [ ] Secrets only in env/keychain; `.env.example` has placeholders.
